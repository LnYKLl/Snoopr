# Snoopr v1 — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** construire Snoopr v1. C'est une appli Windows en Rust qui scanne un disque, affiche un treemap à dossiers imbriqués et permet de supprimer en sécurité ce qui ne sert plus.

**Architecture :** un workspace Cargo avec deux crates.
- `snoopr-core` contient toute la logique : arbre en arène, disposition du treemap, garde-fous, scan parallèle, suppression. Elle n'a aucune interface et elle est testée.
- `snoopr-app` est l'interface `eframe`/`egui`. Elle ne fait que dessiner et appeler le cœur.
- Le scan et les suppressions tournent sur des threads de travail. L'arbre est partagé sous `Arc<RwLock<Tree>>`.

**Tech Stack :** Rust 1.96 stable (édition 2024), `eframe`/`egui` 0.37, `windows` 0.62, `rayon` 1.12, `sys-locale` 0.3, `rfd` 0.17, `tempfile` 3 (tests).

**Spec :** `docs/superpowers/specs/2026-11-03-snoopr-design.md`. La maquette de référence est `docs/superpowers/specs/2026-11-03-snoopr-maquette.html`.

## Global Constraints

- Cible : Windows 10/11 x64 (`x86_64-pc-windows-msvc`). Le cœur garde un repli `cfg(not(windows))` à base de `std` quand ça ne coûte rien. Rien n'est livré hors de Windows.
- Licence : `MIT OR Apache-2.0`.
- L'appli fonctionne **sans droits administrateur**. Le mode admin reste optionnel (« Relancer en administrateur »).
- **Aucun accès réseau** à l'exécution, et aucune crate de télémétrie.
- Les tailles affichées sont des **octets alloués sur le disque** (`AllocationSize`), jamais la taille logique.
- **Rien n'est supprimé sans passer par la fenêtre de confirmation.** En mode corbeille, **jamais de suppression définitive silencieuse**.
- Le thread de l'interface ne fait **jamais** d'énumération de fichiers ni de suppression.
- Tout texte visible vient de `snoopr-app/src/i18n.rs`, en français et en anglais. La langue suit celle de Windows : français si la locale commence par `fr`, anglais sinon.
- L'ancienneté d'un fichier est `max(modifié, créé)`. Celle d'un dossier est le max de ses descendants.
- Les fichiers de test qui touchent le disque utilisent `tempfile::tempdir()`. **Aucun test automatique ne vide la vraie corbeille.**

## Review Focus

1. **Chemins de plus de 260 caractères et noms non ASCII** (accents, emoji) : le scan les lit et la suppression définitive les efface. Tests dans la Tâche 5 (`reads_long_and_unicode_paths`) et la Tâche 8 (`deletes_long_path_tree`).
2. **Jonctions et liens symboliques** : le scan ne les suit pas (pas de boucle, pas de double compte) et la suppression définitive n'efface jamais la cible d'une jonction. Tests dans la Tâche 6 (`junction_loop_is_not_followed`) et la Tâche 8 (`does_not_follow_junction`).
3. **Fichier ouvert par un autre programme** pendant la suppression : il est signalé « utilisé par un autre programme », le reste est supprimé et l'arbre reste cohérent. Tests dans la Tâche 8 (`locked_file_reports_in_use`) et la Tâche 10 (`failed_item_leaves_tree_untouched`).
4. **Élément déjà disparu** (effacé hors de Snoopr après le scan) : il est traité comme supprimé, sans erreur. Tests dans la Tâche 8 (`missing_path_counts_as_removed`) et la Tâche 10 (`removed_permanent_item_is_detached`).
5. **Suppression demandée pendant un scan** (ou un rescan partiel) : le bouton Supprimer est désactivé jusqu'à la fin. Test dans la Tâche 15 (`delete_blocked_while_busy`).

- [ ] **Étape 3 : Implémenter `squarify` et `layout`**

`squarify` suit l'algorithme classique de Bruls et al., comme `squarify()` dans la maquette : on remplit une rangée le long du côté le plus court tant que le pire rapport d'aspect s'améliore.

`layout` procède nœud par nœud :
1. Il prend les enfants de taille > 0, triés par taille décroissante.
2. Il calcule l'aire projetée de chacun (`taille / total × aire intérieure`). Si **au moins 2 enfants** ont une aire inférieure à `min_area`, ils sont fusionnés en un seul `SmallGroup` : `files` = somme des `files`, `size` = somme des tailles. Ce groupe reprend sa place dans le tri par taille.
3. Il applique `squarify` sur ce qui reste.
4. Chaque rectangle est rétréci de `gap/2` sur chaque côté. S'il ne reste pas une largeur et une hauteur strictement positives, il est abandonné.
5. Pour un `Dir` :
   - `header = w >= header_min_w && h >= header_min_h` ;
   - la zone de contenu est `(x+pad, y+header_h, w-2·pad, h-header_h-pad)` avec un bandeau, et un retrait de `pad` sur tous les côtés sans bandeau ;
   - on ne descend dans le dossier (à `depth + 1`) que si cette zone fait au moins `min_side` de large et de haut, et au moins `min_area` en surface.

La racine elle-même n'est pas placée.

4. Préfixe `windows_dir` → WindowsDir. Préfixe `program_data` → ProgramData.
5. Profils :
   - le chemin est `users_dir` → UsersRoot ;
   - son parent est `users_dir` → ProfileRoot ;
   - il est sous `users_dir\Default` → ProfileRoot ;
   - sous un profil, avec les composants relatifs `r` : `r == [appdata]` → AppDataRoot ; `r` commence par `[appdata, roaming, microsoft]`, `[appdata, local, microsoft]` ou `[appdata, local, packages]` → WindowsUserData.

   - les composants consécutifs `steamapps` puis `common`, ou un composant `epic games` ou `xboxgames` → GameLauncher ;

   - extension `pst` ou `ost` → OutlookData ;
   - sous `<profil>\appdata` → AppData.

- [ ] **Étape 3 : Implémenter `start_scan`**

`start_scan` lance un thread dédié. Ce thread crée un pool `rayon` de `clamp(available_parallelism × 2, 4, 32)` threads et exécute `pool.scope(|s| visit(s, under, dir))`. Voici ce que fait `visit` :
1. Il s'arrête tout de suite si le scan est annulé.
2. Il appelle `read_dir_entries`. En cas d'erreur, `NotFound` est ignoré et toute autre erreur incrémente `denied`.
3. Il ignore les entrées `is_link` et convertit les autres en `EntryData`, avec `newest = max(modified, created)`. Un dossier a une taille de 0 ; un fichier a `size = alloc_size`.
4. Il insère ces entrées avec `tree.write().add_children(...)` et garde le verrou le moins longtemps possible.
5. Il lance un `s.spawn` par sous-dossier.
6. Il met à jour `files` et `dirs`. `current` est mis à jour une fois tous les 64 dossiers.

À la fin du scan, `done` passe à vrai et la durée est figée.

  - `NukeOnDelete == 1` → `Disabled` ;
  - `MaxCapacity` (en Mo) → `MaxBytes(mo × 1 048 576)` ;
  - clé absente → `Unknown`.

`recycle` :
1. `CoInitializeEx(COINIT_APARTMENTTHREADED)` sur le thread appelant, en ignorant `S_FALSE` et `RPC_E_CHANGED_MODE`.
2. `CoCreateInstance(&FileOperation)`.
3. `SetOperationFlags(FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI | FOF_WANTNUKEWARNING)`. Ce dernier drapeau est le **filet de sécurité** : Windows demande avant toute destruction non prévue.
4. `SHCreateItemFromParsingName`, puis `DeleteItem` et `PerformOperations`.
5. `GetAnyOperationsAborted()` vrai → `Cancelled`.
6. Ok seulement si le chemin n'existe plus ; sinon, convertir le HRESULT avec `reason_from_hresult`.

Voici la règle de `apply_outcomes` selon le mode et le résultat :

| Mode et résultat | Effet sur l'arbre |
|---|---|
| RecycleBin + `Removed` | Si la racine de l'arbre est une racine de disque, `reparent` sous `ensure_recycle_bin()`. Sinon, `detach`. `freed` ne change pas. |
| Permanent + `Removed` | `freed += size` puis `detach`. |
| `Partial(f)` | `detach`. Un dossier vide du même nom est recréé sous l'ancien parent avec `add_children` (taille 0) et un `Rescan{node: nouveau, path, old_size}` est ajouté. Les échecs `f` sont ajoutés à `failures`. |
| `Failed(f)` | `failures.push(f)`. L'arbre ne change pas. |

L'élément va dans `removed` pour `Removed` et `Partial`.

`reset_view` :
- si `view_root` est un élément de `removed` ou l'un de ses descendants → `(racine, racine)` ;
- sinon, si `selected` est concerné → `(view_root, view_root)` ;
- sinon → inchangé.

- Produces (layout) : `LayoutParams::default()` passe à `header_min_w = 64.0` et `header_min_h = 40.0`. Un `Dir` n'est **parcouru que s'il a un bandeau**. Un `Placed` de `Dir` avec `header == false` est donc un dossier **fermé**, et aucun de ses enfants n'est placé.

**Règles de `child_context(parent, nom, at_drive_root)`** (comparaison insensible à la casse, la première règle qui s'applique gagne) :
1. `parent == System` → System.
2. `at_drive_root` et nom ∈ {`windows`, `system volume information`, `recovery`, `$winreagent`, `boot`, `windows.old`, `$windows.~bt`, `$windows.~ws`} → System.
3. Nom ∈ {`cache`, `caches`, `cache2`, `temp`, `tmp`, `dxcache`, `glcache`, `shadercache`, `gpucache`, `code cache`, `inetcache`, `crashdumps`, `nv_cache`, `d3dscache`} → Cache.
4. Nom ∈ {`steamapps`, `epic games`, `xboxgames`, `riot games`, `gog games`} → Game.
5. `parent` ∈ {Game, Cache, Program} → `parent`.
6. (`at_drive_root` et nom ∈ {`program files`, `program files (x86)`}) ou nom == `windowsapps` → Program.
7. Sinon → None.

**Règles de `file_type(ctx, nom)`** :
1. Le contexte l'emporte : System → System, Cache → Cache, Game → Game.
2. Sinon, par extension (insensible à la casse) :

| Extensions | Type |
|---|---|
| `sys` | System |
| `pak` `vpk` `bsa` `ba2` `ucas` `utoc` `forge` `wad` | Game |
| `mp4` `mkv` `mov` `avi` `wmv` `webm` `m4v` `flv` `ts` `jpg` `jpeg` `png` `gif` `heic` `webp` `raw` `cr2` `nef` `arw` `dng` `psd` `tif` `tiff` `bmp` `mp3` `flac` `wav` `aac` `ogg` `m4a` `opus` | Media |
| `zip` `rar` `7z` `tar` `gz` `bz2` `xz` `zst` `iso` `msi` `msix` `msixbundle` `appx` `cab` | Archive |
| `vhd` `vhdx` `vmdk` `vdi` `qcow2` `avhdx` `img` | VirtualDisk |
| `tmp` `temp` `cache` `dmp` | Cache |
| `exe` `dll` `jar` `pyd` `node` `so` | Program |

3. Sinon, si le contexte est Program → Program.
4. Sinon → Other.

**`root_context(root, rules)`** se déduit de `classify(root)` :
- `Block(WindowsDir | SystemFiles | OldWindows | PageFile | Hiberfil)` → System ;
- `Block(ProgramFiles | WindowsApps)` → Program ;
- `Warn(GameLauncher)` → Game ;
- sinon → None.

**Agrégation :**
- Chaque nœud porte son type de fichier (pour un fichier) ou son contexte (pour un dossier). Ils sont calculés dans `add_children` à partir du contexte du parent.
- `at_drive_root` vaut vrai si le parent est la racine et que la racine est une racine de disque (seulement un préfixe et un séparateur).
- Chaque `Dir` tient un tableau `[u64; 8]` d'octets par type, alloué seulement pour les dossiers (par exemple `Option<Box<[u64; 8]>>`).
- Ce tableau est propagé à tous les ancêtres dans `add_children`, soustrait dans `detach` et rajouté dans `reparent`, au même endroit que `size`.
